# Review of `scripts/Surya/downstream/euv_spectra_subset_eval.py` (2026-11-14)

This is an adversarial review of the EUV-spectra evaluation script against the authors' code (`/home/user/upstream/surya/Surya` at 78b827e, `downstream_examples/euv_spectra_prediction/` and `surya/`), with the fixes made to it. The script turned out to be structurally complete: dry run, sampling, real run, resume and summary were all present. The problems were in robustness and in a few places where a wrong number could have come out without an error. No Surya model was built and no forward pass was run during the review, because another job held about 11 GB of RAM. The dry run was rerun on the rebuilt machine (see the end).

## What was checked and found correct

Model construction follows the authors' path. `config_infer.yaml` goes through `infer.get_model` (from `finetune.py`), which builds `HelioSpectformer1D` with a CLS token, a penultimate linear layer, `unembed` 1280→1343 and a sigmoid. The released weights are then loaded with `load_state_dict(strict=True)`. The checkpoint's key list was read from its pickle header with one 256 KB range request; the checkpoint was not downloaded. It holds 162 float32 tensors: the 157 foundation backbone and embedding keys, plus `cls_token`, `linear.{weight,bias}` and `unembed.{weight [1343,1280], bias}`. It has no LoRA keys and no pretraining decoder. This is exactly the parameter set `get_model` builds for this config (`finetune: True` removes the decoder, and `rpe: false` means no position-bias tables), so the strict load should succeed. The script now also asserts that `infer`, `finetune`, `models` and `dataset` were imported from the EUV task directory, and that the model class is `HelioSpectformer1D`.

Inputs and preprocessing are the authors' unchanged. `EVEDSDataset` is built with `config.yaml`'s 13 channels, `time_delta_input_minutes [0]` (one input frame, dt = 0 h) and the +60 min target frame that the dataset loads and the model never uses. The input frames go through the authors' signum-log scaler. It runs in float32 because `StandardScaler.from_dict` stores np.float32 values. The model runs in float32 with no autocast, under `torch.no_grad`, in eval mode (dropout off), with `num_workers=0`. `scalers.yaml` is copied from Surya-1.0. I checked that it is byte-identical to core-sdo's (sha256 `a944e8f1…`), which is the file `download_data.sh` fetches, and the script now enforces that hash.

The evaluation times and targets are the authors' join. SDO time t comes from core-sdo's `valid_index_surya_1_0.csv` and needs t and t+60 to be present. It is matched to the first EVE time at or after t (`merge_asof` forward), within 6 minutes, keeping the closest t when two map to the same EVE time. The targets are y = (log10 E + 9)/7.04. `finetune.evaluate_model` pools MSE and MAE over all elements on this normalised scale, and Table 5's magnitudes only make sense on it. The paper's text (Sec. 2.6.4, y_t = f(x_t)) confirms that the task maps an image to the spectrum at the same time. The one-sample dataset built for each sampled time pairs it with the same EVE time and gives a bit-identical target. This is checked in the dry run, and in the real run before the forward pass.

MAPE: the paper (v2, appendices included) has no formula for MSE, MAE or MAPE. Its only metric equations are Eqs. 21-23 (TSS, HSS, F1). MAPE is named only in Table 5 and Sec. 2.6.4, where FISM "attains a MAPE of 1.5%", so the unit is percent. The script uses 100/N Σ|ŷ−y|/|y| over all n×1343 normalised elements, with no epsilon. The smallest target in the file is 0.0025. Two variants were fixed in advance and are reported next to it: MAPE over targets ≥ 0.05, and MAPE on de-normalised irradiance.

The checkpoint is downloaded only in the real run, and the dry run reads no weights and no frames.

## Issues found and fixed

1. High: the authors' retry loop. `HelioNetCDFDataset.__getitem__` catches every exception and retries at (idx+1) mod len, up to 100 times. On a multi-sample dataset this silently returns another time's frames, while `EVEDSDataset` attaches the label of the original idx. That is an upstream label-misalignment bug whenever a frame fails to load during the authors' training or validation. On the script's one-sample dataset, it meant re-reading the same two 0.9 GB frames up to 100 times, more than an hour per bad sample. Fixed: a wrapper on the instance's `_get_index_data` (the authors' class and code are unchanged) ends the sample at the first error. The sample is recorded as failed and replaced by its block's reserve. The script also asserts that the frames the dataset reports loading are t and t+60.
2. High: resume and summary mixed sample designs. Earlier records were matched to blocks by (year, block) only. A rerun with another `--seed` or `--n` would have treated the new design's blocks as already done, and `summary.json` would have pooled records from different samples. Fixed: records are matched by time stamp to `sample_<split>.csv`, and the number of ignored records is reported.
3. Medium: the per-sample target checks were computed but not enforced. A label differing from the full-split label would still have been scored. They are now asserted before the forward pass.
4. Medium: there was no RAM guard. A forward pass peaks at 10-13 GB on a 15 GB machine with no swap, and running beside another job could get either one OOM-killed. The run now refuses to start below 12 GB MemAvailable. It also stops cleanly, and can be resumed, before any pass that MemAvailable cannot cover.
5. Medium: frames could leak onto disk. Frames left by an interrupted run, and `.part` files from failed downloads, were never deleted, because `FrameCache` only deletes what it holds in memory. Leftover frames are now adopted (reused or deleted) and partial files removed.
6. Medium: a broken pipeline would only show up at the end. The two notebook anchors run first. If they deviate from the notebook's printout by more than 5e-3 in prediction range or 1e-3 in MAE (far beyond numerical noise), the run now stops instead of spending hours on the sample. `--ignore-anchor-failure` overrides this.
7. Low: a zero or non-finite target would have made MAPE infinite or NaN without any error. It now raises; no such target exists in the file. A line of the jsonl cut off by a crash would have stopped the resume; it is now skipped with a warning. The dry run now warns if a block found no usable candidate, and reports a slow-forward runtime estimate and the available RAM.

## Findings that are not bugs in the script

The released model's patch embedding cannot be the foundation model's. With `time_dim: 1` it has shape [1280,13,16,16] against the foundation's [1280,26,16,16], so `get_model` skips it, and `freeze_backbone: True` then freezes it. If the weights were trained with the repository config, the patch embedding is a random initialisation. The real run records a diagnostic for this in `environment.json`. `infer.load_model` falls back to `strict=False` and carries on after a failed strict load; this script does not fall back. The paper does not state which split, which subset or which checkpoint upload produced Table 5. The script scores both EVE splits and reports them separately.

## Dry run after the fixes

Both dry runs completed (exit 0) on the rebuilt machine, after the EVE file was downloaded again and its sha256 checked. The metric self-test passed: it agrees with `finetune.evaluate_model` to a relative 1e-7 and with `infer.infer_samples` to 5e-7. The test split gave 517 candidate pairs, with 30 primaries and 30 reserves (17 from 2011, 13 from 2014). The validation split gave 355 pairs, with 20 primaries and 20 reserves (12 from 2012, 8 from 2013). No candidate was skipped. Every one-sample dataset reproduced the full-split EVE time and target bit for bit, and both notebook anchors' ground-truth ranges match the printout at 4 decimals. Both sample files are byte-identical to the earlier machine's, so the selection is deterministic. The plan is 32 forward passes for the test split and 20 for the validation split; the validation dry run lists 22 because it counts the anchors, which the test run will already have done. With prefetch, at most 2.4 GB of frames are on disk at once.

## Remaining risks

The strict load and the forward pass have not been executed here, so the first real run is the test of them, and the anchors check them early. The runtime and memory figures (2-5 min and 10-13 GB per pass) come from the other Surya tasks on this machine. The bootstrap resamples time stamps without regard to the year strata, which errs towards wider intervals. The intervals cover sampling within one split only.
