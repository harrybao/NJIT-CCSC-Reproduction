# EUV spectra (Surya paper Table 5): method of the partial reproduction

This is a partial reproduction. The released fine-tuned EUV model is scored on a small, seeded sample of evaluation times on a CPU. It is not the full evaluation set the paper may have used. The script is `scripts/Surya/downstream/euv_spectra_subset_eval.py`. Results go to `summary.json` in this folder once the model has been run. Until then this folder holds only the dry-run outputs (`sample_*.csv`, `sampling_*.json`, `skipped_*.csv`, `metric_check.json`).

## What is evaluated and what it is compared with

The model is `nasa-ibm-ai4science/euv_spectra_surya` at revision `6ed3bc1` (`euv_spectra_weights.pth`, 1,779,722,720 bytes, sha256 `f064836d…`). It maps one set of 13 SDO frames at time t to a 1343-bin SDO/EVE MEGS-A spectrum (6.49-33.33 nm). The reference is the Surya row of Table 5 in arXiv 2508.14112 v2 (Sec. 2.6.4): MSE 0.0001260741, MAE 0.0045114677, MAPE 1.4792510271. For context, the same table gives AlexNet 0.0001311409 / 0.0061858603 / 1.6834715604. The text also says FISM reaches "a MAPE of 1.5% and MSE of 0.00031". The paper's conclusion quotes a Surya MAE of 0.0043, which is not the value in Table 5; we compare with Table 5. For each metric, `summary.json` gives our value on the sample, a 95% percentile bootstrap interval over samples (10,000 resamples), the ratio to the paper value, and whether the paper value lies inside the interval.

## Data and evaluation times

The authors' code (`finetune.py`, `infer.py`, both configs) reads one file of the HF dataset `nasa-ibm-ai4science/euv-spectra`: `archive/AIA_EVE_temporally_stratified.nc` (revision `aafccf9`, 933,907,814 bytes, sha256 checked). It is not the `train/validation/test.csv` files the dataset card describes. The file has three splits, recorded in its `split_rules` attribute. `train_time` has 165,430 spectra from 2010-05-13 to 2014-05-26 (weeks 7-52). `val_time` has 3,275 spectra from Jan 15-28 of 2012 and 2013. `test_time` has 4,880 spectra from Jan 15-28 of 2011 and 2014. All are at 1-minute cadence with gaps, and every value is positive (no zeros or NaNs). The SuryaBench 2020-2024 test period used for the other tasks does not exist here, because MEGS-A stopped in May 2014. So `--split test` means `test_time` and `--split validation` means `val_time`.

The paper does not say which split Table 5 comes from. `finetune.py` validates on `val_time` after every epoch, using at most 200 shuffled batches of one sample. `infer.py` and the tutorial notebook also use `val_time`. No repository code ever reads `test_time`. We therefore score both splits and report them separately: the test split (30 samples) is the primary sample because it was never used for model selection, and the validation split (20 samples) is the one the code itself evaluates.

An evaluation pair is formed exactly as the authors' `EVEDSDataset` forms it on core-sdo's `valid_index_surya_1_0.csv`. That is the SDO index `finetune.py` validates with; it covers Jan 15-31 of 2011-2019, so the foundation model never trained on these days. An SDO time t is usable when t and t+60 min are both indexed. It is paired with the first EVE time at or after t (`merge_asof` forward). Duplicates of an EVE time keep the closest t, and pairs more than 6 minutes apart are dropped. This gives 517 pairs for `test_time` (299 in 2011, 218 in 2014) and 355 for `val_time` (209 in 2012, 146 in 2013). The EVE time falls 4 s to 5 min after t (median 5 s). The candidates are those pairs. For every sampled pair, the script builds a one-sample `EVEDSDataset` whose index holds only t and t+60. It checks that this dataset pairs t with the same EVE time and returns a bit-identical target vector. All 50 sampled pairs, 50 reserves and both anchors passed in the dry run.

## Targets, metrics and units

The dataset turns each spectrum E (W/m²/nm) into y = (log10 E + 9) / 7.04, using fixed bounds of -9.00 and -1.96. Its zero replacement does nothing on this file because there are no zeros. The network ends in a sigmoid and was trained with MSELoss on y. The MSE and MAE in Table 5 must be on this normalised scale: the README and notebook print MAEs of 0.005164 and 0.003811 on it, and on the physical scale the numbers would be many orders of magnitude different. MSE and MAE are pooled over all n_samples × 1343 elements, as `finetune.evaluate_model` pools them. With 1343 bins per sample this equals the mean of the per-sample means.

MAPE is not implemented in the repository, and the paper names it without a formula. We use MAPE = 100/N · Σ |ŷ − y| / |y| over the same N elements, on the normalised scale, in percent. The percent unit follows from the text ("FISM … a MAPE of 1.5%") and the README ("1.48%"). As a fraction, a MAPE of 1.48 would mean errors around 150% of the target, which cannot coexist with an MAE of 0.0045 on targets near 0.6. No target is zero: the smallest is 0.0025 on the test split and 0.0092 on the validation split, set by EVE's floor of about 1.04e-9 W/m²/nm in a few bins near 32.4-33.2 nm. So no epsilon or clipping is applied. Those floor-valued elements are only 0.04% (test) and 0.016% (validation) of all elements, but a prediction of 0.3 against a target of 0.01 has an absolute percentage error of 3000%, so a handful of them can move the mean. Two variants were fixed before any run and are reported next to the primary MAPE: MAPE over elements with y ≥ 0.05 only, and MAPE on the de-normalised irradiance 10^(7.04 y − 9). The median absolute percentage error and the worst elements are reported too. R² and the mean spectral correlation are computed as `infer.py` computes them.

The metric code was checked on synthetic data (`metric_check.json`). It matches the authors' `finetune.evaluate_model` to a relative 1e-7; that function's accumulators are float32, and it reads a module-global `config` that only exists under `__main__`, so the check sets it. It matches the printout of `infer.infer_samples` to its 6 decimals. It gives 15% on a hand example and equals a plain element-by-element loop to 1e-15. It also reproduces `EVEDSDataset`'s normalisation and zero replacement exactly on a synthetic EVE file.

## Sample design

The sample size is split between the two years of a split in proportion to their candidate counts: test 17 for 2011 and 13 for 2014, validation 12 for 2012 and 8 for 2013. Within each year, the time-sorted candidates are cut into equal consecutive blocks of 16-19 pairs, and one pair per block is drawn in an order fixed by seed 0. Before a pair is accepted, both of its frames (t and t+60) must exist on `s3://nasa-surya-bench` (HTTP HEAD) and contain all 13 channels at 4096×4096 (netCDF header read by HTTP range requests). Each block also gets a reserve, which is used only if its primary fails at run time. No candidate was skipped in either split, so `skipped_*.csv` is empty. Each sampled pair stands for an almost equal share of its split. Besides the plain mean, `summary.json` therefore also gives a block-weighted point estimate, which should barely differ from it. Against the full split, the sample's mean target and mean baseline error have z-scores of 0.17 and -0.01 (test) and 0.37 and 0.07 (validation).

The tutorial notebook's saved output works as an end-to-end check. It is a float32 CPU run of `infer.py`, committed on 2025-09-26, after the current checkpoint was uploaded. It covers two `val_time` pairs (SDO 2012-01-15 00:48 and 2013-01-28 18:12) and prints their prediction and ground-truth ranges plus MAE 0.003811, RMSE 0.013978, R² 0.966645 and mean correlation 0.983955. In the dry run, our ground-truth ranges for both pairs equal the printed ones at all 4 decimals. In a real run the two anchors are run first, once over both splits. Their predictions are scored by `infer.infer_samples` itself against the printout, with tolerances fixed in advance (prediction ranges 2e-4, MAE and RMSE 2e-5, R² and correlation 2e-4). They are kept out of the sample metrics unless they are also drawn as validation samples.

A baseline of our own, not part of the paper, is scored on the same samples and on every candidate pair: the constant mean normalised training spectrum. Across all candidates it scores MSE 7.21e-4, MAE 0.0204 and MAPE 4.47% on the test split, and MSE 1.52e-4, MAE 0.0064 and MAPE 1.47% on the validation split. On the validation split this constant prediction is therefore already close to Table 5's Surya row and close to its AlexNet row. Table 5 should be read with that in mind; the paper gives no such baseline.

## How the procedure differs from the paper and the repository, and why

The largest difference is the sample: 30 of 517 test pairs and 20 of 355 validation pairs, instead of whatever full set the paper used. This is a CPU budget limit of about 40 forward passes per run, at roughly 135 s per pass. The bootstrap interval covers sampling variation within the chosen split. It does not cover the uncertainty about which split, which subset (for example `finetune.py`'s 200 shuffled validation batches) or which training epoch produced Table 5.

The checkpoint is the one on HF now. It was uploaded on 2025-08-26 and replaced an upload from 2025-08-18 (1,776,981,576 bytes, sha256 `dd71f11b…`). Both uploads are later than arXiv v1 (2025-08-18), and the current one is also later than v2 (2025-08-21). The paper does not say which weights produced Table 5. The notebook anchors tie our pipeline to the current upload only. The repository's EUV config fine-tunes with a frozen backbone and no LoRA, while the paper credits its downstream results to LoRA. We load the released weights into the architecture of `config_infer.yaml` with `load_state_dict(strict=True)`, exactly as `infer.py` does, and apply no LoRA because `infer.py` applies none.

The model runs in float32 on CPU without autocast. `infer.py`'s `autocast(cpu, float32)` disables itself anyway, and CPU bfloat16 breaks Surya (`results/Surya/bf16_diagnosis`). The authors' GPU runs with `dtype: float32` were also float32, apart from TF32 convolutions that cuDNN may use by default on Ampere GPUs. `torch.load` uses `weights_only=True` with mmap instead of `infer.py`'s `weights_only=False`. If the pickle needs more, `--allow-full-unpickle` restores the original behaviour. Data loading uses `num_workers=0` and a one-sample dataset per pair. The t+60 frame, which the dataset reads into `batch["forecast"]` and the model never uses, is dropped before the forward pass to save 0.87 GB of RAM. Frames come from the public S3 bucket rather than the authors' file system. S3 frames decode bitwise-identically to the HF copies (`results/Surya/s3_vs_hf_frames.json`).

MAPE, its variants, the bootstrap intervals and the baseline are our additions. The unit (percent) and the normalised scale are inferred from the text, not stated. The HF dataset card's split dates (test "Jan 15-31" of 2011 and 2014) do not match the file the code uses, which stops at Jan 28 (weeks 3-4). We follow the file. The card's CSV splits were not opened because each is more than 50 MB.

## Running it

From the repository root, `python scripts/Surya/downstream/euv_spectra_subset_eval.py --split test --n 30 --seed 0` and then `--split validation --n 20 --seed 0` run the model. The first of the two runs also runs the two anchors. The test run is 32 forward passes, about 108 minutes of compute; at 7-8 MB/s from S3 without prefetch it takes about 3 hours. The validation run is 20 passes. `--max-forward K` stops after K passes, and a rerun resumes from `per_sample_<split>.jsonl` and `anchors.jsonl`. The run downloads the 1.78 GB checkpoint into `/home/user/work/surya_ft/euv_spectra/` and keeps at most 2.4 GB of frames on disk (1.2 GB without prefetch). It turns prefetch off when that would leave less than 1 GB free, and stops if even one sample's frames do not fit. `--summarize-only` rebuilds `summary.json` and `per_wavelength_<split>.csv` from the record files.
